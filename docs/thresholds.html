What the threshold is, and is not

Every window gets a reconstruction loss \(\ell(\mathbf{x})\) from the Detector. An alert fires when \(\ell(\mathbf{x}) > \tau_q\). Here \(\tau_q\) is the \(q\)-quantile threshold of the loss for normal windows: a normal window exceeds it with probability \(1 - q\). “The 99.9% threshold” therefore means an exceedance probability of 0.1% per normal window. It is not a confidence level. It is also not adaptive: \(\tau_q\) is estimated once and then fixed. Refitting it on a rolling window or by time of day is listed as further work.

Peaks over threshold (POT). Above a high level \(u\), the excesses \(\ell - u\) are modelled with a Generalized Pareto Distribution (GPD) with scale \(\sigma\) and shape \(\xi\). With \(N\) windows, \(N_u\) of which exceed \(u\),

\[ \tau_q = \begin{cases} u + \dfrac{\sigma}{\xi}\left[\left(\dfrac{N}{N_u}(1-q)\right)^{-\xi} - 1\right], & \xi \neq 0,\\[2ex] u + \sigma \ln\!\left(\dfrac{N_u}{N(1-q)}\right), & \xi = 0 . \end{cases} \]

The second line is the exponential limit. The code (gpd_tau() in R/evt.R) switches to it when \(|\xi| < 10^{-6}\), and a unit test checks that it returns a finite value at \(\xi = 0\).

Held-out fitting. The GPD is fitted to losses from the 4 validation hosts (16,128 windows), which the autoencoder never trained on. Training losses are biased low, because the model has seen those windows. Their fit is kept only as a comparison row. We set \(u\) at the 95% quantile.

How to read the table. Each row is one fit of the tail model. \(u\) is the loss level above which the tail is modelled, and \(N_u\) counts how many windows exceed it. \(\sigma\) sets the spread of the tail and \(\xi\) its shape: positive means occasional very large values, zero means an exponential tail, negative means a hard ceiling. Standard errors are in brackets. The τ columns are the resulting alert thresholds, shown beside the plain sample quantiles.

What the table tells you. The held-out tail is heavy, with \(\xi = 0.381\) and a resampling range of 0.27 to 0.49. Fitting on training losses would have set a lower 99.9% threshold (2.635 against 3.559) and raised more false alarms on new hosts. The fitted threshold sits below the plain sample quantile (4.004), because the tail contains a step of count-driven spikes that a smooth curve cannot follow.

The choice of \(u\) and the GPD fit are assumptions. These plots test whether the assumptions are reasonable.

How to read the plots. Left: the average amount by which losses exceed each candidate cut-off. Above a suitable cut-off this line should be roughly straight. Middle and right: the tail model’s adjusted scale and its shape \(\xi\), refitted at fifteen cut-offs between the 85% and 99% quantiles, with 95% intervals as vertical bars. A suitable cut-off is one above which these estimates stay flat. The dashed red line marks the cut-off actually chosen.

What the plots tell you. There is no stable region. The shape estimate keeps rising with the cut-off, from 0.19 at the 90% quantile to 0.68 at the 99% quantile, and the mean-excess line curves upward instead of straightening. One smooth tail model does not describe these losses well, because they mix ordinary errors with discrete count spikes. The chosen cut-off is a compromise, and the 99.9% threshold moves between 3.29 and 3.71 depending on it.

Thresholds and their uncertainty

EVT earns its place when the alert rate must be far lower than 0.1%, below the range where the data contain enough examples. At a security operations centre (SOC) scoring 1,000,000 windows a day, even 0.1% means 1,000 alerts a day.

How to read the table. Each row is a rarer alert level. “EVT τ” is the threshold from the fitted tail. The interval columns show its range when the analysis is repeated on resampled data, keeping whole host-days together so neighbouring windows stay linked. “Empirical quantile” is the plain data answer, shown only where at least 10 held-out windows exceed it. The last column is benign alerts per day at 1,000,000 windows a day.

What the table tells you. The 99.9% threshold is 3.559 with an interval of 3.059–4.201: a range, not a precise value. Beyond 99.99% the data hold too few examples for a plain answer, so the fitted tail is the only basis for a threshold, and its intervals widen sharply (10.0–33.6 at 99.999%). Those rarer levels are what a large security operations centre would need to keep alert volumes manageable.

Calibration on new hosts

A threshold meant to produce 0.1% false alarms should produce about 0.1% on hosts it was not fitted on. This table checks that.

Display code 
cal |>
  mutate(q_lab = paste0(formatC(100 * q, format = "f", digits = 3), "%")) |>
  select(q_lab, tau, n_normal, expected_fp, observed_fp, p_value) |>
  gt() |>
  tab_header(title = "Observed vs Expected False Alarms", subtitle = "Clean test hosts, main seed; exact binomial test") |>
  cols_label(q_lab = "Quantile q", tau = "τ", n_normal = "Normal windows", expected_fp = "Expected",
             observed_fp = "Observed", p_value = "Binomial p-value") |>
  fmt_number(tau, decimals = 3) |>
  fmt_number(expected_fp, decimals = 1) |>
  fmt_integer(n_normal) |>
  fmt_number(p_value, decimals = 3) |>
  tab_options(table.font.size = 12)

How to read the table. For each alert level, “Expected” is how many of the 8,064 normal test windows should cross the threshold if it were exactly right, and “Observed” is how many did. These windows come from hosts that were not used to set the threshold. The p-value says how surprising the gap would be by chance alone. Values below about 0.05 suggest the threshold is genuinely off rather than unlucky.

What the table tells you. At 99.9% the test hosts produced 16 false alarms against 8.1 expected (p = 0.012). At 99% they produced 61 against 80.6. The threshold is off in both directions, because each host has its own baseline. Across 30 seeds, false alarms at 99.9% ranged from 1 to 52. Thresholds set per host or per role would be the natural fix.

Clustering of alerts

Exceedances are not independent: one busy period produces several high-loss windows in a row. The extremal index \(\theta\) measures this. \(1/\theta\) is the average number of exceedances per cluster. We estimate it with the runs method: exceedances within 3 windows of each other belong to one cluster.

Display code 
theta <- dc$theta
tibble(q = q[1:3]) |>
  mutate(
    q_lab = paste0(formatC(100 * q, format = "f", digits = 2), "%"),
    windows = (1 - q) * vol,
    incidents = theta * windows
  ) |>
  select(q_lab, windows, incidents) |>
  gt() |>
  tab_header(title = "From Window Exceedances to Distinct Alert Clusters",
             subtitle = sprintf("Extremal index θ = %.2f; volume %s windows per day", theta, f_int(vol))) |>
  cols_label(q_lab = "Quantile q", windows = "Normal windows alerting / day", incidents = "Distinct clusters / day") |>
  fmt_number(c(windows, incidents), decimals = 0) |>
  tab_options(table.font.size = 12)

How to read the table. Alerts tend to arrive in bursts: one busy period produces several high-loss windows in a row. The first column is the number of benign windows per day that would cross each threshold at 1,000,000 windows a day. The second groups windows that fire within 3 windows of each other into a single cluster. That is closer to the number of separate incidents an analyst must actually open and close.

What the table tells you. The extremal index of 0.80 means about 1.3 exceedances per cluster on average, so grouping cuts the triage load only modestly: 807 exceedances form 645 clusters. The tail shape barely changes when fitted to cluster peaks (\(\xi = 0.358\)). Even at the 99.99% level this detector alone would raise about 80 benign alert clusters a day at this volume, far too many to act on automatically.

Values below about 0.05 suggest the threshold is genuinely off rather than unlucky.

**What the table tells you.** At 99.9% the test hosts produced `r cal$observed_fp[2]` false alarms against `r f_num(cal$expected_fp[2], 1)` expected (p = `r f_num(cal$p_value[2], 3)`). At 99% they produced `r cal$observed_fp[1]` against `r f_num(cal$expected_fp[1], 1)`. The threshold is off in both directions, because each host has its own baseline. Across `r n_seeds` seeds, false alarms at 99.9% ranged from `r f_num(rob_get("False alarms at 99.9%")$lo, 0)` to `r f_num(rob_get("False alarms at 99.9%")$hi, 0)`. Thresholds set per host or per role would be the natural fix.

## Clustering of alerts

Exceedances are not independent: one busy period produces several high-loss windows in a row. The extremal index $\theta$ measures this. $1/\theta$ is the average number of exceedances per cluster. We estimate it with the runs method: exceedances within `r cfg$evt$decluster_run_length` windows of each other belong to one cluster.

```{r}
#| label: tbl-decluster
theta <- dc$theta
tibble(q = q[1:3]) |>
  mutate(
    q_lab = paste0(formatC(100 * q, format = "f", digits = 2), "%"),
    windows = (1 - q) * vol,
    incidents = theta * windows
  ) |>
  select(q_lab, windows, incidents) |>
  gt() |>
  tab_header(title = "From Window Exceedances to Distinct Alert Clusters",
             subtitle = sprintf("Extremal index θ = %.2f; volume %s windows per day", theta, f_int(vol))) |>
  cols_label(q_lab = "Quantile q", windows = "Normal windows alerting / day", incidents = "Distinct clusters / day") |>
  fmt_number(c(windows, incidents), decimals = 0) |>
  tab_options(table.font.size = 12)
```

**How to read the table.** Alerts tend to arrive in bursts: one busy period produces several high-loss windows in a row. The first column is the number of benign windows per day that would cross each threshold at `r f_int(vol)` windows a day. The second groups windows that fire within `r cfg$evt$decluster_run_length` windows of each other into a single cluster. That is closer to the number of separate incidents an analyst must actually open and close.

**What the table tells you.** The extremal index of `r f_num(theta)` means about `r f_num(1 / theta, 1)` exceedances per cluster on average, so grouping cuts the triage load only modestly: `r f_int(dc$n_exceed)` exceedances form `r f_int(dc$n_clusters)` clusters. The tail shape barely changes when fitted to cluster peaks ($\xi = `r f_num(dc$fit$estimate[["shape"]], 3)`$). Even at the 99.99% level this detector alone would raise about `r f_int(theta * vol * 1e-4)` benign alert clusters a day at this volume, far too many to act on automatically.
