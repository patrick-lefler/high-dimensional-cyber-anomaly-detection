Abstract

Signature rules and fixed thresholds miss attacks that stay inside normal ranges. This project tests a two-layer alternative, built in R, on simulated enterprise telemetry.

The structural layer models 23 services as a Markov transition matrix of call flows. It ranks them by PageRank, articulation points and a node-removal simulation, and turns the ranking into criticality tiers that decide which alerts may trigger automated containment.

The detection layer is a shallow autoencoder, written in base R with analytic gradients and Adam. It is trained on 19 correlated, seasonal telemetry features. Alerts fire when reconstruction loss exceeds a threshold fitted to the loss tail with a Generalized Pareto Distribution on held-out hosts.

Results. Across 30 independent seeds (mean [95% range]):

  • The autoencoder separates attacks from normal windows with ROC AUC 0.794 [0.734–0.824]. Mahalanobis distance does better (0.817 [0.765–0.843]), so the network adds nothing over simpler statistics on this data.
  • At the 99.9% threshold it catches 77.0% [63.8%–82.0%] of high-intensity attacks, 24.6% [19.1%–34.3%] of medium and 0.8% [0.2%–2.1%] of low.
  • It misses data exfiltration at every intensity.
  • False alarms at 99.9% were 14.1 [1.5–52.2] per 8,064 normal windows, against about 8 expected. The threshold does not transfer cleanly to new hosts.
  • The loss tail is heavy (shape ξ = 0.24 [0.10–0.38]), driven by rare benign count spikes.

The two-layer design is sound. The detector, as built, is not ready for automated response.

These results come from simulated data and injected attacks, not production telemetry. They show how the method behaves, not how it would perform in a real enterprise.

Introduction

Enterprise systems produce large volumes of authentication, network and host telemetry. Most monitoring still relies on fixed signatures and static thresholds, which miss attacks that stay inside normal ranges. Credential stuffing spread across many sources and slow data exfiltration are examples. An unsupervised detector learns what normal looks like and flags departures from it, so it can in principle catch attacks nobody has written a rule for.

Detection alone is not enough. The usual response to an alert is containment: isolate a host, revoke a token. If the affected service sits under much of the estate, the containment can cause a larger outage than the attack. This project therefore pairs the detector with a structural model of service dependencies. Together they answer two questions: is this window abnormal? and how dangerous is it to act on that automatically?

WarningRead this first

Every number on this site comes from a simulation with assumed parameters (params.yaml). The results show how the methods behave under controlled conditions. They do not estimate how the system would perform on any real network.

Techniques

Markov transition matrix. Services are nodes, and an edge \(i \to j\) means service \(i\) calls service \(j\). Normalizing call volumes by row gives \(P_{ij} = \Pr(\text{next call goes to } j \mid \text{at } i)\), a row-stochastic matrix. It assumes the next hop depends only on the current service (first-order Markov). Details →

PageRank. PageRank is the long-run share of request hops landing on each service, with random restarts weighted by a damping factor. It measures dependency concentration. It is not a single-point-of-failure detector, so it is cross-checked against articulation points and a node-removal simulation.

Shallow autoencoder. A 19-4-19 network with a \(\tanh\) bottleneck and a linear decoder, trained only on normal windows. Each window is scored by its mean squared reconstruction error \(\ell(\mathbf{x}) = \tfrac{1}{d}\lVert \mathbf{x} - \hat{\mathbf{x}} \rVert^2\). With one hidden layer it is close to principal component analysis, and the results confirm this. Details →

Extreme Value Theory (peaks over threshold). Losses above a high level are modelled with a Generalized Pareto Distribution. This gives quantile thresholds \(\tau_q\) for exceedance probabilities too small to estimate directly from the data. The thresholds come with bootstrap intervals, diagnostics and a calibration test. Details →

How to read the table. Each row is one result, averaged over 30 complete re-runs of the study, each with fresh simulated data, a newly trained model and a newly fitted threshold. ROC AUC runs from 0.5, no better than a coin toss, to 1, complete separation of attacks from normal activity. Detection rates are the share of attack windows that raised an alert. The 2.5% and 97.5% columns bracket the middle 95% of re-runs.

What the table tells you. The detector reliably catches loud attacks and misses quiet ones: 77.0% of high-intensity windows but 0.8% of low-intensity ones, and almost no data exfiltration. It does no better than Mahalanobis distance, a classical statistic that needs no training. False alarms average 14.1 against about 8 expected and vary several-fold between runs. The original AUC of 1.0 came from the simulation design, not the model.

Recommendations

We recommend three governance practices:

  1. Human-in-the-loop containment, routed by criticality. Alerts on Tier 1 services (Key Management, File Store, DNS Resolver, API Gateway, Notification Svc, Customer Service) require human approval before isolation or credential revocation, because isolating them is itself an outage. Automate only low-blast-radius actions, such as step-up authentication or ending a single session, and only after the detector has been validated on production telemetry. At realistic attack rates most alerts at the 99.9% threshold would be false alarms (see the base-rate table), so automated isolation today would mostly hit healthy hosts.

  2. Explain every alert, and test the explanations. Report the top three contributing features with each alert. Measure how often they point at the true cause, and compare them against plain z-scores, which did as well here. This aligns with the explainability and model-risk expectations in the NIST AI Risk Management Framework (voluntary) and OSFI Guideline E-23 (effective May 1, 2027 for federally regulated Canadian financial institutions). Neither one prescribes a specific detector.

  3. Monitor drift by effect size, not significance. Replace weekly per-feature KS tests with Wasserstein distance per feature (in standard-deviation units, with an effect-size trigger). Track the live alert rate against its expected \(1-q\), and refit and re-validate the threshold on a schedule. In the drift test, KS flagged harmless shifts every time, and PSI at standard cut-offs missed a material one.

Limitations

What would change the conclusions:

  • Simulated data. The latent factors, marginals, correlations, seasonality and host roles are all assumptions. Real telemetry has missing data, logging changes, holidays and populations of very different hosts. Client data would replace the generator in R/sim.R: at least four weeks of host-by-window telemetry with an asset inventory.
  • Simulated attacks. Each attack changes a few features in single windows or short runs. Real campaigns move across hosts and over days. Labelled red-team or incident data would replace params.yaml: attacks.
  • Heavy, discrete tail. Rare count features dominate extreme normal losses, so a single GPD fits poorly and the threshold depends on the chosen level \(u\). Per-host or per-role thresholds, or separate models for count features, may change the picture.
  • Fixed threshold. \(\tau_q\) is fitted once. Thresholds that adapt over time, by rolling refit or by time of day, are not implemented.
  • Dependency graph. The graph, call volumes and tier cut-offs are illustrative. The first-order Markov assumption is stated, not tested. Service-mesh call logs and session traces would replace them.
  • Prevalence. The test set is about 28% attacks. Real environments are orders of magnitude lower, which is why the base-rate table matters more than the ROC curve.

What changed from the original version

An independent review found that the original single-page report:

  • advertised a Markov/PageRank layer it never built;
  • simulated independent features (so the 0.75 loss plateau was a mathematical floor, not learning);
  • used attacks pushed far outside normal ranges;
  • reported single-seed results with no uncertainty.

This version builds the dependency layer and adds correlated, seasonal data with three attack intensities. The detector is compared against baselines over 30 seeds. The EVT threshold is fitted on held-out hosts, with diagnostics and calibration tests. The headline results changed accordingly.

Reproducibility

  1. Install packages with pak (see the session information below). Package versions are not pinned with renv, so the session information below is the record of what produced these results.
  2. Run Rscript run_all.R from the project root. It regenerates every result in results/ in under a minute.
  3. Run Rscript -e 'testthat::test_dir("tests/testthat")' for the unit tests: GPD threshold including \(\xi = 0\), gradient check, transition matrix and PageRank, removal impact, drift metrics, AUC, and the simulator.
  4. Run quarto render. Pages read the cached results. Because freeze: auto is on, delete _freeze/ after re-running run_all.R so every page re-executes.

All parameters and seeds are in params.yaml: main seed 42, robustness seeds 1–30, graph seed 7. Each seeded run is deterministic and does not depend on the number of parallel workers.

```{r}
  mutate(across(c(mean, lo, hi), \(x) case_when(fmt == "pct" ~ f_pct(x), fmt == "int" ~ f_num(x, 1), .default = f_num(x, 3)))) |>
  select(label, mean, lo, hi) |>
  gt() |>
  tab_header(title = sprintf("Headline Results across %d Seeds", n_seeds),
             subtitle = sprintf("False alarms out of %s normal test windows; about %.0f expected at 99.9%%",
                                f_int(n_normal_test), n_normal_test * 0.001)) |>
  cols_label(label = "Quantity", mean = "Mean", lo = "2.5%", hi = "97.5%") |>
  tab_options(table.font.size = 12)
```

**How to read the table.** Each row is one result, averaged over `r n_seeds` complete re-runs of the study, each with fresh simulated data, a newly trained model and a newly fitted threshold. ROC AUC runs from 0.5, no better than a coin toss, to 1, complete separation of attacks from normal activity. Detection rates are the share of attack windows that raised an alert. The 2.5% and 97.5% columns bracket the middle 95% of re-runs.

**What the table tells you.** The detector reliably catches loud attacks and misses quiet ones: `r f_pct(rob_get("high", "Detection at 99.9% by intensity")$mean)` of high-intensity windows but `r f_pct(rob_get("low", "Detection at 99.9% by intensity")$mean)` of low-intensity ones, and almost no data exfiltration. It does no better than Mahalanobis distance, a classical statistic that needs no training. False alarms average `r f_num(fa999$mean, 1)` against about `r f_num(n_normal_test * 0.001, 0)` expected and vary several-fold between runs. The original AUC of 1.0 came from the simulation design, not the model.

## Recommendations

We recommend three governance practices:

1. **Human-in-the-loop containment, routed by criticality.** Alerts on Tier 1 services (`r paste(tier1, collapse = ", ")`) require human approval before isolation or credential revocation, because isolating them is itself an outage. Automate only low-blast-radius actions, such as step-up authentication or ending a single session, and only after the detector has been validated on production telemetry. At realistic attack rates most alerts at the 99.9% threshold would be false alarms (see the [base-rate table](evaluation.qmd#base-rates)), so automated isolation today would mostly hit healthy hosts.

2. **Explain every alert, and test the explanations.** Report the top three contributing features with each alert. Measure how often they point at the true cause, and compare them against plain z-scores, which did as well here. This aligns with the explainability and model-risk expectations in the [NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework/ai-risk-management-framework-faqs) (voluntary) and [OSFI Guideline E-23](https://www.osfi-bsif.gc.ca/en/guidance/guidance-library/guideline-e-23-model-risk-management-2027) (effective May 1, 2027 for federally regulated Canadian financial institutions). Neither one prescribes a specific detector.

3. **Monitor drift by effect size, not significance.** Replace weekly per-feature KS tests with Wasserstein distance per feature (in standard-deviation units, with an effect-size trigger). Track the live alert rate against its expected $1-q$, and refit and re-validate the threshold on a schedule. In the [drift test](evaluation.qmd#drift-monitoring), KS flagged harmless shifts every time, and PSI at standard cut-offs missed a material one.

## Limitations

What would change the conclusions:

- **Simulated data.** The latent factors, marginals, correlations, seasonality and host roles are all assumptions. Real telemetry has missing data, logging changes, holidays and populations of very different hosts. Client data would replace the generator in `R/sim.R`: at least four weeks of host-by-window telemetry with an asset inventory.
- **Simulated attacks.** Each attack changes a few features in single windows or short runs. Real campaigns move across hosts and over days. Labelled red-team or incident data would replace `params.yaml: attacks`.
- **Heavy, discrete tail.** Rare count features dominate extreme normal losses, so a single GPD fits poorly and the threshold depends on the chosen level $u$. Per-host or per-role thresholds, or separate models for count features, may change the picture.
- **Fixed threshold.** $\tau_q$ is fitted once. Thresholds that adapt over time, by rolling refit or by time of day, are not implemented.
- **Dependency graph.** The graph, call volumes and tier cut-offs are illustrative. The first-order Markov assumption is stated, not tested. Service-mesh call logs and session traces would replace them.
- **Prevalence.** The test set is about `r f_pct(n_attack_test / (n_attack_test + n_normal_test), 0)` attacks. Real environments are orders of magnitude lower, which is why the base-rate table matters more than the ROC curve.

## What changed from the original version

An independent review found that the original single-page report:

- advertised a Markov/PageRank layer it never built;
- simulated independent features (so the 0.75 loss plateau was a mathematical floor, not learning);
- used attacks pushed far outside normal ranges;
- reported single-seed results with no uncertainty.

This version builds the dependency layer and adds correlated, seasonal data with three attack intensities. The detector is compared against baselines over `r n_seeds` seeds. The EVT threshold is fitted on held-out hosts, with diagnostics and calibration tests. The headline results changed accordingly.

## Reproducibility

1. Install packages with `pak` (see the session information below). Package versions are not pinned with `renv`, so the session information below is the record of what produced these results.
2. Run `Rscript run_all.R` from the project root. It regenerates every result in `results/` in under a minute.
3. Run `Rscript -e 'testthat::test_dir("tests/testthat")'` for the unit tests: GPD threshold including $\xi = 0$, gradient check, transition matrix and PageRank, removal impact, drift metrics, AUC, and the simulator.
4. Run `quarto render`. Pages read the cached results. Because `freeze: auto` is on, delete `_freeze/` after re-running `run_all.R` so every page re-executes.

All parameters and seeds are in `params.yaml`: main seed `r cfg$seeds$main`, robustness seeds 1–`r cfg$seeds$robustness`, graph seed `r cfg$graph$seed`. Each seeded run is deterministic and does not depend on the number of parallel workers.
